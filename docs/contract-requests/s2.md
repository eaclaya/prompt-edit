# S2 contract requests

## 1. S1's "still a stub" test goes red once S2 lands (test-only, no contract change)

**Problem.** `tests/Feature/Foundation/ContractsTest.php`, `it('resolves every contract to a stub …')`, asserts
that `CostCalculator`, `Markup`, `CostEstimator` and `PricingCatalog` throw `NotImplementedException`.
Once `PricingServiceProvider` binds the real classes (the S2 deliverable), those four dataset rows fail.

S3 raised the same thing for `Ledger` (`docs/contract-requests/s3.md` on its branch).

**Requested change (smallest).** Drop the four S2 rows (and the imports only they used) from that dataset.
S2's own `tests/Unit/Pricing/PricingServiceProviderTest.php` asserts each contract now resolves to its
real implementation, so nothing loses coverage.

**Status.** Until S1/S8 answers, S2 applies exactly this to its branch as **one isolated commit**
("Stub test skips the pricing contracts now that S2 implements them"), easy to drop or replace when S8
reconciles the dataset across S2/S3/S5. Expect a trivial conflict with S3's edit to the same dataset.

No change to contracts, DTOs, config, routes or schema.

## 2. (FYI, not blocking) unknown token types

PLAN.md §7 asks that "missing or unknown token types fail loudly". With the contract's DTOs an unknown
type can't reach `CostCalculator` (`Usage`/`Rates` have exactly the four `TokenType` fields, and the
calculator walks `TokenType::cases()`), and missing types already throw in `Usage::fromArray()` /
`Rates::fromArray()` — S2 tests both. `Usage::fromArray()` silently ignores *extra* keys (it must accept
`total_tokens`). If S1/S8 wants a new token type in an API payload to fail loudly, that is a change to
`App\Contracts\Data\Usage::fromArray()` (S1-owned), e.g. reject keys outside `TokenType` ∪ {`total_tokens`}.
S2 has not made it.
