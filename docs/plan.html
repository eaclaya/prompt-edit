PromptEdit × Pixelforge: build plan

Laravel + Inertia + Vue. Users generate images through Pixelforge and pay its cost plus 25%. Every cost is recorded exactly once, failed generations are free, and duplicate or out-of-order webhooks can't corrupt state.

Summary

Exact money

Integer nano-dollars (10⁻⁹ USD) in bigint. No floats.

Never charged twice

Ledger with UNIQUE(generation_id, type), enforced by the database.

Forward-only state

One transition service for webhooks and polling.

Honest estimates

Show a min–max range and hold the max. Users are never charged more than they were shown.

Resilient submission

Redis queue, a stable Idempotency-Key, and shared Redis rate limiting.

Reconcilable

Costs booked on the UTC completion day, matching /v1/usage.

Money & pricing

Unit: 1 = $0.000000001. A rate of $R per 1M tokens = R × 1000 nano-dollars per token. User price = ceil(cost × 125 / 100), which is exact at today's rates.

Estimate & actual-cost algorithms 
// Estimate — rates from GET /v1/pricing (cached 1 h in Redis)
chars    = mb_strlen(prompt, 'UTF-8')                // Unicode chars, not bytes
textEst  = ceil(chars / 4)
textMin  = floor(textEst * 0.85)   textMax = ceil(textEst * 1.15)
fixed    = 765*refs*rI + OUTPUT[q][size]*rO          // exact part
costMin  = fixed + textMin*rT + REASON[q].min*rR
costMax  = fixed + textMax*rT + REASON[q].max*rR
priceMin = markup(costMin)   priceMax = markup(costMax)  // priceMax is held

// Actual — rates from the generation object itself
cost  = Σ usage[k] * nano(gen.rates[k])   for k in text, image, output, reasoning
price = markup(cost)

Submission

Web request: validate (prompt ≤ 4,000 chars, allowed size and quality, ≤ 4 http(s) URLs) → estimate on the server → in a transaction, lockForUpdate the user, check balance ≥ priceMax, insert the pending generation and write the HOLD → SubmitGeneration::dispatch()->afterCommit().

Job (queue submissions, retryUntil 15 min, unique per generation; no-op if no longer pending):

OutcomeActionUser sees
202 (incl. replay)apply(payload)Queued
429 concurrencyrelease(Retry-After ?? 5)Waiting for capacity
429 rate limitrelease(Retry-After + jitter)Waiting for capacity
503 overloadedrelease(min(2·2ⁿ, 60) + jitter)Provider busy, retrying
Timeout / connection error / 5xxRetry with the same keySubmitting…
400 content policyFail locally + RELEASEBlocked by policy. Not charged.
429 daily limitFail locally + RELEASEDaily limit; resets 00:00 UTC.
422 / 409 / 401Fail + RELEASE + report()Error on our side. Not charged.
Window exhaustedFail (local.retries_exhausted) + RELEASEToo busy. Not charged.
Fail locally only on definitive rejections, which create nothing at the provider. An ambiguous timeout is always retried with the same key, never marked failed.

State transitions

  • Find the generation by provider_id or metadata.local_id, with lockForUpdate inside a transaction.
  • Fill in provider_id if it's missing (the early-webhook case).
  • If the current status is final or rank(new) ≤ rank(current), stop: no-op.
  • Succeeded: store tokens, cost and price → ledger RELEASE + CHARGE → dispatch StoreGenerationImage after commit.
  • Failed: store the error, price = 0 → ledger RELEASE.
Sketch 
public function apply(GenerationPayload $p): void
{
    DB::transaction(function () use ($p) {
        $g = Generation::where('provider_id', $p->id)
            ->orWhere('id', $p->metadata['local_id'] ?? null)
            ->lockForUpdate()->firstOrFail();
        $g->provider_id ??= $p->id;
        if ($g->status->isFinal() || $p->status->rank() <= $g->status->rank()) {
            $g->save(); return;
        }
        $g->fill($p->timestampsAndRates());
        match ($p->status) {
            Status::Succeeded => $this->settleSuccess($g, $p),
            Status::Failed    => $this->settleFailure($g, $p),
            default           => null,
        };
        $g->save();
    });
}

Three independent guards: event-id deduplication, the rank check under a row lock, and the ledger's unique index.

Webhooks

  • POST /webhooks/pixelforge, CSRF-exempt, no session.
  • Parse Pixelforge-Signature: t=…,v1=…. Reject if |now − t| > 300 or no hash_equals(hmac_sha256("t.rawBody", secret), v1) → 400.
  • ping → 200.
  • insertOrIgnore into webhook_events. A duplicate increments attempts_seen and returns 200.
  • Dispatch ProcessWebhookEvent on the high-priority webhooks queue and return 200 at once.

Each write: a transaction, lock the user row, insert the entry, increment balance_nano. A unique-constraint violation means it was already applied, so it's a no-op. php artisan ledger:verify asserts balance == SUM(entries).

Image storage

  • StoreGenerationImage (queue default, 5 tries with backoff): download image_url → generations/{ulid}.png on a private S3-compatible disk → set image_path.
  • Served through an authorised route /generations/{id}/image (owner or admin), which redirects to a short-lived temporaryUrl.
  • If the copy hasn't been made yet, fall back to the provider URL until image_url_expires_at, then show an "Image expired" placeholder.
  • Download failure never affects billing; it's a separate job after commit.

Admin report

  • /admin/report?start&end, gated by is_admin. Default 30 days, maximum 92.
  • By day (UTC completed_at) and by user: generations, tokens, provider cost, credit spend, profit, margin, failed count.
  • Reconciliation: /v1/usage for the same range next to our per-day totals → ✓ match or Δ $x, compared as integers.
Query sketch 
SELECT DATE(completed_at) AS day, COUNT(*) AS generations,
       SUM(input_text_tokens), SUM(input_image_tokens), SUM(output_tokens), SUM(reasoning_tokens),
       SUM(provider_cost_nano) AS provider_cost, SUM(price_nano) AS credit_spend,
       SUM(price_nano - provider_cost_nano) AS profit
FROM generations
WHERE status = 'succeeded' AND completed_at >= :start AND completed_at < :end_plus_1
GROUP BY day ORDER BY day;   -- by user: GROUP BY user_id

  • Feature: duplicate and out-of-order events, early webhook, failed → $0, every submit outcome via Http::fake, polling + webhook → one charge, ledger invariant, insufficient funds, report across UTC midnight, image fallback.

Deployment (Laravel Cloud)

  1. Public GitHub repo → Cloud app (PHP 8.4, npm ci && npm run build).
  2. Attach Postgres, a Redis-compatible key-value store and an object storage bucket.
  3. Worker: queue:work redis --queue=webhooks,submissions,default; enable the scheduler.
  4. Env: APP_TIMEZONE=UTC, QUEUE_CONNECTION=redis, CACHE_STORE=redis, PIXELFORGE_API_KEY, PIXELFORGE_WEBHOOK_SECRET, MARKUP_BPS=2500, filesystem disk.
  5. Deploy command migrate --force; seed the admin once.
  6. Production Pixelforge key → webhook https://<app>/webhooks/pixelforge → ping → 200.
  7. Smoke test with normal, [fail], [duplicate], [slow] and [blocked] prompts; check the report against /v1/usage; leave them on the site.

Local: Herd (prompt-edit.test), Redis via Herd services or Homebrew, a separate local key, and herd share / ngrok for webhooks.

Interview notes

Why nano-dollars?

Exact to the provider's precision; integer arithmetic; rounding only for display.

Why hold the max?

It's a promise to the user, and it makes concurrent submits safe against the balance.

Why Redis?

A shared atomic throttle across workers, queue priorities, and fast locks. The DB queue can't share a rate budget well.

Rates change?

Actual cost uses the generation's own rates; the markup rounds up to the nano-dollar.
